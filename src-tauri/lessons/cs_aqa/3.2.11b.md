## What it is

**Testing** means running an algorithm or program with chosen data, and comparing what it actually does with what it **should** do. Its purpose is to **find errors** so they can be corrected, and to show that the program **meets its requirements** and copes with every kind of input it might receive, including mistakes. Testing cannot prove a program has no errors at all, but well-chosen tests find most of them. You test throughout development (each subroutine as it is written) and again at the end (the whole program).

Algorithms can be tested before any code exists, by a **dry run**: working through the pseudo-code by hand with a **trace table** (3.1.1b) and checking the outputs.

**Test data.** You cannot try every possible input, so you choose a small set that covers the important cases. AQA names three types:

| Type | Meaning | For a mark accepted from 1 to 10 inclusive |
|---|---|---|
| **Normal** (typical) | Data the program should accept and process, well inside the allowed range | 5, 7 |
| **Boundary** (extreme) | Data **at** the edges of the allowed range and **just either side** of them | 0, 1, 10, 11 |
| **Erroneous** | Data that should be **rejected**: the wrong type or far outside the range | 'seven', −30, 200 |

**Boundary data** is where programs most often go wrong, because `<` and `≤` are easy to confuse. AQA's own definition takes values **either side** of each limit, so for 1 to 10 the boundary set is 0 and 1 at the bottom, 10 and 11 at the top. 1 and 10 should be **accepted**; 0 and 11 should be **rejected**. If a program uses `mark < 10` where it should use `mark ≤ 10`, only testing 10 reveals it.

Other kinds of rule have boundaries too:
- A password must be at least 8 characters: boundary data is a 7-character and an 8-character password.
- A whole number of tickets, 1 to 6: boundary data is 0, 1, 6, 7.
- A real number from 0.0 to 5.0: boundary data includes 0.0 and 5.0, and values just outside such as −0.1 and 5.1.

**Erroneous data** includes data of the wrong **type** (letters where a number is expected, a blank where text is required) and values that make no sense (a negative age). A robust program (3.2.11a) rejects them without crashing.

**Selecting and justifying test data.** In an exam you may have to choose data and say **why**. A good justification links the value to its type and the expected result: "11 is boundary data just above the limit, and should be rejected with an error message". A simple **test plan** sets this out:

| Test | Data | Type | Expected result |
|---|---|---|---|
| 1 | 6 | Normal | Accepted, and processed |
| 2 | 1 | Boundary | Accepted |
| 3 | 10 | Boundary | Accepted |
| 4 | 11 | Boundary | Rejected, 'Out of range' shown |
| 5 | 'six' | Erroneous | Rejected, error message shown |

When the tests are run, an **actual result** column is filled in. If actual and expected results differ, there is an error to fix, and the test is run again afterwards to check the fix worked.

**Types of error.** The spec names two, and you must be able to identify and categorise them:

| | Syntax error | Logic error |
|---|---|---|
| What it is | Code that breaks the **rules (grammar)** of the programming language | Code that is valid but does **the wrong thing** |
| When found | When the code is translated; the program **will not run** | When the program runs and gives an **unexpected / incorrect result** |
| Error message? | Yes: the translator reports it, usually with a line number | No: the program runs, so testing must reveal it |
| Examples | Misspelt keyword (`pirnt`), missing bracket or colon, `ENDIF` missing, `=` instead of `←` for assignment in some languages | `<` instead of `≤`, `+` instead of `-`, wrong variable used, loop running one time too few, a total reset inside a loop |

Logic errors are harder to find because nothing tells you they are there. They are found by testing with carefully chosen data and by tracing.

**Finding and correcting errors.** Exam questions give numbered code and ask for the line number and a corrected line. For example, this algorithm should output the average of 5 numbers:
1. `total ← 0`
2. `FOR i ← 1 TO 5`
3. `    total ← 0`
4. `    n ← STRING_TO_INT(USERINPUT)`
5. `    total ← total + n`
6. `ENDFOR`
7. `OUTPUT total / 4`

- Line 3 resets the total on every pass, so only the last number counts. It is a **logic** error. Correction: delete line 3.
- Line 7 divides by 4 instead of 5. **Logic** error. Corrected line: `OUTPUT total / 5`.

And a Python fragment that will not run:
1. `count = 0`
2. `for i in range(10)`
3. `    if i % 2 == 0:`
4. `        count = count + 1`
5. `print("Even:", count`

- Line 2 is missing its colon: **syntax** error. Corrected: `for i in range(10):`
- Line 5 is missing a closing bracket: **syntax** error. Corrected: `print("Even:", count)`

**How to find a logic error.** Choose test data whose correct answer you know, trace the code with it, and look for the first line where a variable takes a value you did not expect. Boundary data is particularly good at this.

::: terms
- **Testing**: running an algorithm or program with chosen data to find errors and check it meets its requirements.
- **Test data**: input values chosen to check that a program works correctly in different situations.
- **Normal data**: typical data that the program should accept and process correctly.
- **Boundary data**: data at the limits of the allowed range and just either side of them, e.g. 0, 1, 10 and 11 for 1 to 10.
- **Erroneous data**: data that should be rejected because it is of the wrong type or outside the allowed range.
- **Test plan**: a table listing each test, its data, the type of data and the expected result.
- **Syntax error**: an error where code breaks the rules of the language, so it cannot be translated and run.
- **Logic error**: an error where the program runs but produces an unexpected or incorrect result.
- **Dry run**: working through an algorithm by hand, often with a trace table, to check it works.
:::

::: method
1. **Find the rule** being tested: the lowest and highest allowed values, or the minimum length.
2. **Normal:** pick a value comfortably inside the range.
3. **Boundary:** take each limit and the value just outside it (for 1 to 10: 0, 1, 10, 11). State which are accepted and which rejected.
4. **Erroneous:** pick the wrong type (text for a number) or a value far outside the range.
5. **Expected result:** say exactly what should happen (accepted and processed, or rejected with a message), not just "it works".
6. **Categorising an error:** would the program refuse to run? Syntax. Does it run but give a wrong answer? Logic.
7. **Correcting an error:** give the **line number** and rewrite the **whole corrected line**.
:::

::: example Choosing test data
A program accepts a shoe size from 3 to 12 inclusive (whole numbers). Complete a test plan with one normal, two boundary and one erroneous test, giving the expected result of each. (4)

| Data | Type | Expected result |
|---|---|---|
| 7 | Normal | Accepted (1) |
| 3 | Boundary | Accepted (1) |
| 13 | Boundary | Rejected (1) |
| 'big' | Erroneous | Rejected with an error message (1) |

Accept 2, 12 for boundary; any value from 4 to 11 for normal; any non-integer or far-out value for erroneous.
:::

::: example Categorise errors
State whether each is a syntax error or a logic error: (a) `ENDWHILE` is missing at the end of a loop; (b) a program to find the largest number uses `<` instead of `>`; (c) `OUTPUT 'Total: ' total` is missing the comma. (3)

(a) Syntax: the loop structure breaks the language rules (1).

(b) Logic: the code runs but finds the smallest instead of the largest (1).

(c) Syntax: the statement is not written in a valid form (1).
:::

::: example Find and correct
This algorithm should output 'Pass' for marks of 40 or more.
1. `mark ← STRING_TO_INT(USERINPUT)`
2. `IF mark > 40 THEN`
3. `    OUTPUT 'Pass'`
4. `ELSE`
5. `    OUTPUT 'Fail'`
6. `ENDIF`

Identify the line containing the error, state its type, and write the corrected line. (3)

Line 2 (1). Logic error: a mark of exactly 40 outputs 'Fail' (1). Corrected line: `IF mark ≥ 40 THEN` (1).
:::

::: example Justify the data
Explain why testing a program with only normal data is not enough. (2)

Normal data only shows the program works for typical values (1); errors at the limits (such as `<` used for `≤`) or a failure to reject invalid data would not be found, so boundary and erroneous data are also needed (1).
:::

::: example Which test finds it
A range check should accept 1 to 100 but is coded `IF n > 1 AND n ≤ 100 THEN`. State which test value would reveal the error and why. (2)

1 (1): it should be accepted, but `n > 1` rejects it, so the actual result differs from the expected result (1).
:::

::: q
State the purpose of testing a program. (1)
---
To find errors / to check the program works correctly and meets its requirements (1).
:::

::: q
A program accepts ages from 11 to 18 inclusive. State all four boundary values. (2)
---
10, 11, 18, 19 (2). 1 mark for two or three correct.
:::

::: q
Give an example of erroneous data for a program that asks for the number of pets a person owns, and justify it. (2)
---
E.g. 'three' / −2 / 2.5 (1); it is the wrong type / impossible value and should be rejected (1).
:::

::: q
Describe the difference between a syntax error and a logic error. (2)
---
A syntax error breaks the rules of the language, so the program cannot be translated / run (1); a logic error lets the program run but it gives an incorrect or unexpected result (1).
:::

::: q
Explain why logic errors are usually harder to find than syntax errors. (2)
---
The translator reports syntax errors, usually with a line number (1); a logic error produces no error message, so it is only found if testing shows a wrong result (1).
:::

::: q
This Python line should add 1 to `score`: `score + 1 = score`. State the type of error and correct it. (2)
---
Syntax error, because the assignment is written the wrong way round (1). `score = score + 1` (1).
:::

::: watch
- **Boundary data** is on **and either side of** each limit. For 1 to 10 give **0, 1, 10, 11**; giving only 1 and 10 loses marks.
- Say whether boundary values should be **accepted or rejected**.
- Erroneous data must be data that should be **rejected**. A valid but unusual value is not erroneous.
- Only two error types are examined: **syntax** and **logic**. A wrong answer from a program that runs is **logic**.
- When correcting code, give the **line number** and the **full corrected line**, not just the changed symbol.
- "Expected result" means what **should** happen, decided before the test, not what the program actually did.
:::

D — it is the wrong data type and should be rejected.

Define the term boundary data. (1)
---
Data at the limits of the allowed range / just either side of the limits (1).
:::

::: test
State one way a syntax error is detected. (1)
---
The translator (compiler / interpreter) reports it when the code is translated, so the program will not run (1).
:::

::: test
A password must be at least 8 characters long. Describe two pieces of boundary test data and the expected result of each. (2)
---
A password of exactly 8 characters, which should be accepted (1); a password of 7 characters, which should be rejected (1).

::: test
Explain why boundary data is important when testing a program that uses selection. (2)
---
Errors are often made in the comparison operators at the limits, e.g. `<` instead of `≤` (1); testing exactly on and either side of the limit shows whether the limit itself is handled correctly (1).
:::

::: test
A program calculates delivery charges. Orders of £50 or more get free delivery; smaller orders cost £4. Order values are whole pounds and must be between £1 and £500. Complete a test plan with four tests: one normal, two boundary for the free-delivery rule, and one erroneous. Give the expected result for each. (4)
---
One mark per correct row with data, type and expected result, e.g.:
- 20, normal, £4 delivery charged (1).
- 49, boundary, £4 charged (1).
- 50, boundary, free delivery (1).
- 'ten' / −5 / 600, erroneous, rejected with an error message (1).
Accept other valid values, e.g. 51 for a boundary test, or 1 and 0 / 500 and 501 for the range boundaries.
:::

::: test
The algorithm below should output the largest of five numbers entered.
1. `largest ← 0`
2. `FOR i ← 1 TO 4`
3. `    n ← STRING_TO_INT(USERINPUT)`
4. `    IF n < largest THEN`
5. `        largest ← n`
6. `    ENDIF`
7. `ENDFOR`
8. `OUTPUT largest`
Identify the two lines that contain errors and write the corrected lines. (4)
---
Line 2 (1): the loop runs only 4 times; `FOR i ← 1 TO 5` (1).
Line 4 (1): the comparison finds smaller values; `IF n > largest THEN` (1).
:::

::: test
The Python program below should output the times table for a number entered, from 1 to 12, but it contains errors.
1. `num = int(input("Number: ")`
2. `for i in range(1, 12):`
3. `    print(i, "x", num, "=", i * num)`
(a) Identify the syntax error and correct it. (b) Identify the logic error and correct it. (4)
---
(a) Line 1 is missing a closing bracket (1): `num = int(input("Number: "))` (1).
(b) Line 2: range(1, 12) stops at 11, so the 12 line is missing (1): `for i in range(1, 13):` (1).
:::

::: test
State the error type in each case: (a) the program crashes on startup because `WHILE` was typed as `WHIEL`; (b) a program meant to count down from 10 counts up instead. (2)
---
(a) Syntax error (1). (b) Logic error (1).
:::

::: test
A programmer tests a validation routine for an age from 11 to 16 using only the values 13 and 14. Explain why this testing is not thorough enough and suggest additional test data. (3)
---
Only normal data is used, so errors at the limits or with invalid input would not be found (1). Add boundary data: 10, 11, 16, 17 (1). Add erroneous data, e.g. 'twelve' or −4 (1).
:::

::: test
A student's program should output 'Valid' for a year from 2000 to 2030 inclusive. Their condition is `IF year > 2000 AND year < 2030 THEN`. Using test data, explain how the error would be found and how to correct it. (3)
---
Testing the boundary values 2000 and 2030 (1) would output 'Invalid' although both should be valid, so actual and expected results differ (1). Correct the condition to `year ≥ 2000 AND year ≤ 2030` (1).
:::

::: test
An algorithm is designed to accept a rating from 1 to 5 and output the average of all the ratings entered. Describe how a programmer should test it, referring to the types of test data and to how errors are corrected. (6)
---
Award up to 6 from:
- Draw up a test plan before testing, listing data and expected results (1).
- Normal data such as 3, checking it is accepted and included in the average (1).
- Boundary data 0, 1, 5 and 6, checking 1 and 5 are accepted and 0 and 6 rejected (1).
- Erroneous data such as 'good' or a blank, checking it is rejected without the program crashing (1).
- Check the average calculation with data whose answer is known, e.g. 2 and 4 gives 3 (1).
- Compare actual results with expected results; where they differ, trace / dry run the code to locate the error (1).
- Correct the error and re-run the tests (including earlier ones) to check the fix (1).
:::

::: test
The algorithm below should count how many of the numbers entered are from 10 to 20 inclusive. The user enters 5 numbers.
1. `count ← 0`
2. `FOR i ← 1 TO 5`
3. `    n ← STRING_TO_INT(USERINPUT)`
4. `    IF n > 10 AND n ≤ 20 THEN`
5. `        count ← count + 1`
6. `    ENDIF`
7. `ENDFOR`
8. `OUTPUT count`
Complete a trace for the inputs 9, 10, 15, 20, 21, giving the value of count after each input and the final output. Then state the expected output, identify the error, and write the corrected line. (6)
---
- A. 9: count stays 0 (1).
- B. 10: count stays 0, because 10 > 10 is False (1).
- C. 15: count 1; 20: count 2; 21: count stays 2 (1).
- D. Output 2 (1).
- E. Expected output is 3, because 10 should be counted (1).
- F. Line 4 is a logic error; corrected line `IF n ≥ 10 AND n ≤ 20 THEN` (1).
:::
