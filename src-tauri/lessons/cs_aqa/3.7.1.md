## What it is

Almost every organisation keeps its data in a **database**: a school's pupil records, a shop's stock list, a library's loans, a gym's members. This topic is the theory behind them. The next topic (3.7.2) is SQL, the language you use to get data in and out. Paper 2 always has a database question: a figure showing two or three small tables, then short questions on the terms, a 6-mark SQL query and a 2–3 mark INSERT, UPDATE or DELETE.

### What a database is

A **database** is a **persistent, organised collection of structured data**, stored so that it can easily be **searched, sorted, added to, changed and deleted** by software.
- **Persistent** means it is kept in secondary storage and is still there after the program closes or the computer is switched off.
- **Organised and structured** means the data is held in a fixed layout (tables of rows and columns), not as free text, so a computer can find exactly the item it needs.

The software that manages the database is a **database management system** (DBMS). You don't need to know its details; you write SQL and the DBMS does the work.

### Tables, records and fields

Data in a database is stored in **tables**. Each table holds data about **one kind of thing**: members, classes, books, customers, orders.

Here is a table from a gym's database:

**Member**

| MemberID | FirstName | LastName | Phone | Plan | Joined |
|---|---|---|---|---|---|
| M001 | Asha | Patel | 07700900123 | Gold | 03/01/2025 |
| M002 | Tom | Reid | 07700900456 | Basic | 17/02/2025 |
| M003 | Grace | Okoye | 07700900789 | Gold | 09/04/2025 |

- A **record** is **one row**: all the data about **one item** in the table. Row M002 is one record, everything stored about Tom Reid.
- A **field** is **one column**: a **single item of data** stored for every record, such as LastName or Plan. Each field has a name and a data type.
- The **table** is the whole collection of records about that kind of thing.

A quick check: "how many records?" means count the **rows** (3 above, not counting the header); "how many fields?" means count the **columns** (6).

### Data types

Every field has a **data type**, which fixes what can be stored in it and how the DBMS handles it. The types you should use in answers:

| Data type | Use it for | Example field |
|---|---|---|
| **Integer** | whole numbers you might count or calculate with | YearGroup, Quantity, Age |
| **Real** (float, decimal) | numbers with a fractional part, including money | Price, DepositPaid, Height |
| **Text / String** | letters, or a mixture of letters and digits | LastName, Postcode, MemberID |
| **Boolean** | exactly two values, True or False | Paid, IsMember |
| **Date / Time** | dates and times | Joined, DateOfBirth |
| **Character** | a single character | Grade, Initial |

Two classic traps:
- A **phone number** is stored as **text**, not integer. It can start with **0**, which an integer would drop, may contain spaces or a +, and you never do arithmetic on it.
- **Money** is **real** (or currency/decimal), not integer, because it has pence. An ID such as **M001** is **text**, because it contains a letter.

### Primary key

A **primary key** is a field that **uniquely identifies each record** in a table. No two records may have the same value, and it must never be left empty.

In the Member table the primary key is **MemberID**. It is a good choice because:
- every member gets a different ID, whereas two members could share a **name** (two people called Tom Reid) or a **plan**;
- it never needs to change, whereas a phone number or surname can change.

That is why databases usually invent an ID field (MemberID, OrderID, CopyID) rather than relying on real-world data. When asked "why is LastName not a suitable primary key?", the answer is that **two records could have the same value**, so it would not identify one record uniquely.

### Foreign key and relational databases

A **relational database** stores data in **several tables** that are **linked (related)** to each other using **keys**. The link is made by a **foreign key**.

A **foreign key** is a field in one table that is the **primary key of another table**. It holds the value that points to the matching record in the other table.

The gym has two more tables:

**Class**

| ClassID | ClassName | Day | Instructor |
|---|---|---|---|
| C10 | Spin | Monday | Lee |
| C11 | Yoga | Tuesday | Sam |
| C12 | Boxfit | Monday | Lee |

**Booking**

| BookingID | MemberID | ClassID | Paid |
|---|---|---|---|
| B501 | M001 | C10 | True |
| B502 | M003 | C10 | False |
| B503 | M001 | C11 | True |
| B504 | M002 | C12 | True |

- In Booking, the primary key is **BookingID**.
- **MemberID** in Booking is a **foreign key**: it is the primary key of the Member table.
- **ClassID** in Booking is also a **foreign key**: it is the primary key of the Class table.

To find who booked B502, take its MemberID (M003) and look it up in Member: Grace Okoye. To find which class, take C10 and look it up in Class: Spin on Monday.

Notice that one member can appear in **many** bookings (M001 has two), but each booking belongs to **one** member. Unlike a primary key, a foreign key value **can repeat** in its own table. That is often how you spot one in an exam: a field whose name matches the primary key of another table, with values that repeat.

### Why not keep everything in one table?

A database with everything in one table is a **flat file**. Here is the same gym data as one big table:

| BookingID | FirstName | LastName | Phone | ClassName | Day | Instructor | Paid |
|---|---|---|---|---|---|---|---|
| B501 | Asha | Patel | 07700900123 | Spin | Monday | Lee | True |
| B502 | Grace | Okoye | 07700900789 | Spin | Monday | Lee | False |
| B503 | Asha | Patel | 07700900123 | Yoga | Tuesday | Sam | True |
| B504 | Tom | Reid | 07700900456 | Boxfit | Monday | Lee | True |

Two problems follow.

**Data redundancy** means the **same data is stored more than once, unnecessarily**. Asha's name and phone number are stored twice, and every Spin booking repeats "Monday" and "Lee". With thousands of bookings, this wastes a lot of **storage** and makes the table slower to process.

**Data inconsistency** means **copies of the same data no longer match**. Suppose Asha changes her phone number. Somebody updates row B501 but misses B503. Now the database holds two different numbers for her, and nobody can tell which is right. The more copies there are, the more likely this is, and the same happens if a name is misspelt in one row.

There are knock-on problems too: you cannot store a new member who has not booked anything yet without leaving booking fields blank, and deleting a member's only booking deletes everything known about them.

### How a relational database fixes this

Splitting the data into **separate linked tables** means each fact is stored **once only**:
- each member's details are stored in **one record** in Member;
- each class's details are stored in **one record** in Class;
- Booking only stores the **keys** (MemberID, ClassID) plus data that belongs to the booking itself (Paid).

So:
- **Redundancy is reduced**: the only repeated values are short foreign keys, not whole names and phone numbers.
- **Inconsistency is eliminated**: a change (Asha's new number) is made in **one place**, and every booking that links to M001 automatically sees the new value.
- Data is easier to **maintain**, a member can exist with no bookings, and less storage is used.

The spec puts it as relational databases **facilitating the elimination** of inconsistency and redundancy. In an answer, always link the two: **less duplicated data means fewer copies that can disagree**.

### Spotting keys in an exam figure

1. For each table, the **primary key** is the field whose values are **all different**, usually an ID field, often the first column.
2. A **foreign key** is a field in one table that has the **same name (and values) as the primary key of a different table**.
3. A table can have **one primary key** but **several foreign keys**, as Booking does.
4. Not every table has a foreign key: Member and Class above have none, because they are the tables being pointed to.

AQA uses the words **table, record, field**, not entity and attribute, both for real databases and for designs on paper. Use AQA's words in your answers.

::: terms
- **Database**: a persistent, organised collection of structured data that software can search, sort and update.
- **Relational database**: a database that stores data in separate tables linked to each other by primary and foreign keys.
- **Table**: a set of records about one kind of thing, such as members or classes, set out in rows and columns.
- **Record**: one row of a table, holding all the data stored about one item, such as one member.
- **Field**: one column of a table, a single item of data stored for every record, such as LastName.
- **Data type**: the kind of data a field can hold, such as integer, real, text, Boolean or date.
- **Primary key**: a field whose value uniquely identifies each record in a table; it cannot repeat or be empty.
- **Foreign key**: a field in one table that is the primary key of another table, used to link the two tables.
- **Flat file**: a database held as a single table, so the same details are often repeated many times.
- **Data redundancy**: the same data being stored more than once unnecessarily, wasting storage.
- **Data inconsistency**: copies of the same data that do not match, for example two different phone numbers for one person.
:::

::: method
1. **Read the figure first.** For each table, note what one record represents and which field is the ID.
2. **Primary key:** give the field whose values are unique for every record. If asked why another field is unsuitable, say two records **could share** that value.
3. **Foreign key:** give a field in one table that is the **primary key of another table**, and name that other table if asked.
4. **Data type:** look at the actual values. Pence means **real**; leading zeros or letters mean **text**; True/False means **Boolean**; whole counts mean **integer**.
5. **Redundancy / inconsistency:** quote the repeated data **from the given table**, say it is stored more than once (redundancy), then say an update to one copy could miss the others, so copies disagree (inconsistency).
6. **"Why split into tables?":** each fact stored **once**, linked by keys; change made in **one place**; less storage; no conflicting copies. Apply it to the named fields.
:::

::: example Identify the keys
A cinema's database has two tables: Film(FilmID, Title, Certificate, Minutes) and Screening(ScreeningID, FilmID, ScreenNumber, StartTime). State the primary key of Screening, and state the foreign key in Screening. (2)

Primary key: ScreeningID (1). Foreign key: FilmID (1), because it is the primary key of the Film table.
:::

::: example Choose data types
State the most suitable data type for each of these fields in the Film table: Title, Minutes, and a field Subtitled that shows whether a film has subtitles. (3)

Title: text/string (1). Minutes: integer (1). Subtitled: Boolean (1).
:::

::: example Why not this primary key
A school proposes using LastName as the primary key of its Student table. Explain why this is not suitable. (2)

A primary key must uniquely identify each record (1), but two students could have the same last name, so a LastName value would not identify one student (1).
:::

::: example Redundancy in a given table
A vet's surgery stores every appointment in one table with the fields AppointmentID, OwnerName, OwnerPhone, PetName, Species, Date. Explain why this design causes data redundancy and how that could lead to inconsistency. (4)

An owner with several appointments has their name and phone number stored again in every appointment record (1), which is data redundancy: the same data stored more than once unnecessarily (1). If the owner changes their phone number, every one of those records must be updated (1); if one is missed, the table holds two different phone numbers for the same owner, which is data inconsistency (1).
:::

::: example Benefit of a relational design
Explain one benefit of storing the vet's data in separate Owner, Pet and Appointment tables linked by keys. (2)

Each owner's details are stored only once, in the Owner table (1), so a change of phone number is made in one place and every linked appointment uses the new value, removing inconsistency (1).
:::

::: q
Define the term record in a database. (1)
---
One row of a table / all the data stored about one item, e.g. one customer (1).
:::

::: q
Explain what is meant by a relational database. (2)
---
A database made of more than one table (1), where the tables are linked/related using primary keys and foreign keys (1).
:::

::: q
A table Product has the fields ProductCode, Description, Price, InStock, Quantity. State the most suitable data type for Price and for InStock. (2)
---
Price: real/float/decimal/currency (1). InStock: Boolean (1). Reject integer for Price.
:::

::: q
Explain why a customer's phone number should be stored as text rather than as an integer. (2)
---
It may start with a zero, which would be lost if stored as an integer (1); it may contain spaces or a +, and no calculations are ever done on it (1).
:::

::: q
State two properties that a primary key must have. (2)
---
Unique for every record / no two records share a value (1); must not be empty/blank (1). Accept: should not change.
:::

::: q
A table Order has the fields OrderID, CustomerID, OrderDate, Total. CustomerID is the primary key of the Customer table. Explain why CustomerID is a foreign key in Order. (2)
---
It is a field in the Order table that is the primary key of another table, Customer (1); it links each order to the customer who placed it (1).
:::

::: watch
- A **foreign key** is the **primary key of another table**. "A key that links tables" or "a key from somewhere else" is too vague for the mark.
- **Record = row, field = column.** Swapping them is the commonest one-mark loss.
- Use the **table and field names in the figure**, spelt exactly. Inventing a field name loses the mark.
- **Phone numbers and IDs with letters are text**; **money is real**. Integer for money is rejected.
- "Saves space" alone is thin. For redundancy questions, say the **same data is stored more than once**; for inconsistency, say **copies could be updated differently**.
- Primary key answers need **uniqueness**. "It's the ID" without "unique" rarely scores.
:::

State the difference between a primary key and a foreign key. (2)
---

::: test

---

::: test
Explain why data redundancy can lead to data inconsistency. (2)
---
When data is stored in several places, every copy must be changed when it is updated (1); if one copy is missed or changed differently, the copies no longer match, so the database holds conflicting values (1).
:::

::: test
A tutoring company stores all its data in one table.

| LessonID | StudentName | StudentEmail | Subject | TutorName | TutorRate |
|---|---|---|---|---|---|
| L01 | Jamal Hussain | jh@mail.uk | Maths | Ms Cole | 30.00 |
| L02 | Ruby Lane | rl@mail.uk | Physics | Mr Ade | 28.00 |
| L03 | Jamal Hussain | jh@mail.uk | Physics | Mr Ade | 28.00 |
| L04 | Jamal Hussain | jh@mail.uk | Maths | Ms Cole | 30.00 |

Explain why the company should store this data in a relational database with separate tables rather than in this one table. (4)
---
Max 4 from, applied to the table:
- Jamal Hussain's name and email are stored three times / tutors' names and rates repeat in several rows (1), which is data redundancy (1).
- If a value changes, e.g. Jamal's email or Mr Ade's rate, every copy must be updated (1); missing one leaves conflicting values, which is data inconsistency (1).
- With separate Student, Tutor and Lesson tables, each student's and tutor's details are stored once (1) and Lesson links to them with foreign keys such as StudentID and TutorID (1), so a change is made in one place (1) and less storage is used (1).
:::

::: test
For the tutoring company in the previous question, describe a relational design. Name each table, list its fields, and identify every primary key and foreign key. (6)
---
1 mark each, max 6:
- A Student table with a StudentID primary key plus StudentName, StudentEmail (1).
- A Tutor table with a TutorID primary key plus TutorName, TutorRate (1).
- A Lesson table with a LessonID primary key (1) plus Subject (1).
- Lesson contains StudentID as a foreign key (1).
- Lesson contains TutorID as a foreign key (1).

::: test
A field in a Customer table is called Postcode. A student says its data type should be integer. Explain why the student is wrong. (2)
---
UK postcodes contain letters and a space as well as digits (1), so they must be stored as text/string; an integer can hold only whole numbers (1).
:::

::: test
Explain why a new database might give each customer a CustomerID instead of using their email address as the primary key. (2)
---
An email address can change, and a primary key should not change because foreign keys in other tables refer to it (1); a generated ID is guaranteed to be unique and short, whereas emails are long and may be shared, e.g. by a family (1).
:::
