## What it is

A **subroutine** is a named block of code that sits **out of line**, separate from the main program, and runs only when it is **called** by writing its name in a statement. When the call happens, control jumps to the subroutine, its code runs, and control then **returns** to the line after the call. Subroutines are how real programs are built: instead of one long list of instructions, the program is split into small, named jobs.

In AQA pseudo-code:
1. `SUBROUTINE greet(name)`
2. `    OUTPUT 'Hello ' + name`
3. `ENDSUBROUTINE`
4. `greet('Ada')`
5. `greet('Alan')`

Lines 1–3 **define** the subroutine; nothing happens when they are read. Lines 4 and 5 **call** it, so the output is 'Hello Ada' then 'Hello Alan'. In Python the same subroutine is `def greet(name):` with an indented body, called with `greet("Ada")`.

**Procedures and functions.** The spec groups both under "subroutines":
- A **function** returns a value to the code that called it, using `RETURN`. The call is used as a value, inside an expression or assignment: `area ← rectArea(4, 5)`.
- A **procedure** does a job (such as outputting a menu) but returns nothing. The call is a statement on its own: `showMenu()`.

**Parameters** pass data **into** a subroutine. The names in the subroutine's heading are its parameters; the values written in the call are copied into them in order. AQA uses the word **parameter** for both (some books call the values in the call *arguments*). A subroutine can take several parameters, separated by commas:
1. `SUBROUTINE rectArea(width, height)`
2. `    area ← width * height`
3. `    RETURN area`
4. `ENDSUBROUTINE`
5. `a ← rectArea(4, 5)`
6. `OUTPUT a`

Here 4 goes into `width` and 5 into `height`, because the order matches. The output is 20.

**Return values** pass data **out**. `RETURN area` ends the subroutine and sends the value of `area` back to the calling routine, where it replaces the call: line 5 becomes `a ← 20`. The returned value must be **used**: stored, output, or put in a condition. A call such as `rectArea(4, 5)` written alone throws the answer away. In Python, `return area`; in C#, the method has a return type such as `static int RectArea(int w, int h)`; in VB.NET, a `Function … As Integer` with `Return`.

**Local variables.** A variable created inside a subroutine, like `area` above, is **local**:
- it **exists only while the subroutine is running**; it is created when the subroutine starts and destroyed when it ends;
- it is **only accessible inside that subroutine**; the main program cannot read or change it.

Parameters behave as local variables too. A variable declared in the main program, outside every subroutine, is **global**: it can be seen everywhere. Because locals are private, two subroutines can each have a variable called `total` with no clash.

**Why using local variables is good practice:**
- A subroutine cannot accidentally change a variable used elsewhere, so bugs stay contained.
- The same names can be reused in different subroutines without conflict.
- The subroutine is **self-contained**: everything it needs comes in through parameters and everything it produces goes out through the return value, so it can be tested on its own and reused in another program.
- Memory used by locals is freed when the subroutine ends.

**Tracing calls.** Follow the values in, then the value out:
1. `SUBROUTINE bigger(x, y)`
2. `    IF x > y THEN`
3. `        RETURN x`
4. `    ELSE`
5. `        RETURN y`
6. `    ENDIF`
7. `ENDSUBROUTINE`
8. `m ← bigger(7, 12)`
9. `OUTPUT bigger(m, 9) + 1`

Line 8: x = 7, y = 12, so 12 is returned and m = 12. Line 9: x = 12, y = 9, so 12 is returned, then 1 is added: the output is 13. Note that a subroutine can have more than one RETURN, but only one runs on each call.

**Advantages of subroutines:**

| Advantage | Why it helps |
|---|---|
| Code written once, called many times | Programs are shorter; there is less to type and less to get wrong |
| Easier to maintain | A fix or change is made in **one place** and every call benefits |
| Easier to test and debug | Each subroutine can be tested on its own with chosen parameters |
| Easier to read | A well-named call like `calculateVAT(price)` says what the code does |
| Team working | Different programmers can write different subroutines at the same time |
| Reuse | A tested subroutine can be copied into, or imported by, other programs |

**The structured approach.** Structured programming means designing a program as a set of **modules** (subroutines), each doing one clear task, usually found by **decomposing** the problem (3.1.1). Each module has a **clear, well-documented interface**: its name, the parameters it takes (and their data types), and the value it returns, with a comment saying what it does. Inside, it uses **local variables**, so it communicates with the rest of the program only through its parameters and return value. The main program then reads like a summary:
1. `marks ← getMarks()`
2. `avg ← mean(marks)`
3. `grade ← gradeFor(avg)`
4. `printReport(avg, grade)`

**Advantages of the structured approach:** the program is easier to understand, because each part is small and named; modules can be written and tested independently, so errors are easier to find and fix; modules can be shared out across a team; well-defined interfaces mean one module can be changed or replaced without breaking the others, as long as its parameters and return value stay the same; and tested modules can be reused in other projects, saving development time.

::: terms
- **Subroutine**: a named, out-of-line block of code that runs when it is called by name from elsewhere in the program.
- **Call**: a statement that runs a subroutine by writing its name, with any parameters in brackets.
- **Parameter**: a value passed into a subroutine when it is called, received by a named variable in the subroutine heading.
- **Return value**: the value a function sends back to the calling routine, where it replaces the call.
- **Function**: a subroutine that returns a value.
- **Procedure**: a subroutine that carries out a task but does not return a value.
- **Local variable**: a variable declared inside a subroutine that exists only while it runs and can only be used inside it.
- **Global variable**: a variable declared in the main program that can be accessed anywhere in the program.
- **Structured approach**: designing a program as modules with clear, documented interfaces that pass data by parameters and return values.
- **Interface**: the name, parameters and return value of a subroutine; how the rest of the program uses it.
:::

::: method
1. **Identify the parts:** the heading (name and parameters), the body, any RETURN, and the calls in the main program.
2. **For a trace:** at each call, copy the values into the parameters **in order**, run the body, and replace the call with the returned value.
3. **For "identify" questions:** parameters are in the heading's brackets; local variables are assigned inside the body; the return value follows RETURN.
4. **For "explain an advantage":** name the advantage, then link it to its effect ("…written once and called many times, so the program is shorter and a change only needs making in one place").
5. **When writing a subroutine:** give it a meaningful name; take every input it needs as a parameter (do not use USERINPUT unless asked); use local variables; RETURN the result rather than outputting it when the question says "returns".
6. **When calling it:** pass parameters in the right order and **use** the returned value (assign it, output it or test it).
:::

::: example Identify the parts
1. `SUBROUTINE discount(price, percent)`
2. `    saving ← price * percent / 100`
3. `    newPrice ← price - saving`
4. `    RETURN newPrice`
5. `ENDSUBROUTINE`
6. `cost ← discount(80, 25)`

(a) State the identifier of a parameter. (b) State the identifier of a local variable. (c) State the value of `cost` after line 6. (3)

(a) `price` or `percent` (1).

(b) `saving` or `newPrice` (1).

(c) 60: saving = 80 × 25 / 100 = 20, and 80 − 20 = 60 (1).
:::

::: example Function or procedure
Explain the difference between a function and a procedure, using an example of each. (2)

A function returns a value to the calling routine, e.g. a subroutine that returns the area of a rectangle (1). A procedure carries out a task without returning a value, e.g. a subroutine that outputs a menu (1).
:::

::: example Local variables
Explain two reasons why it is good practice to use local variables in subroutines. (4)

A local variable can only be accessed inside its subroutine (1), so the subroutine cannot accidentally change a value used elsewhere in the program, which avoids hard-to-find bugs (1).

A local variable only exists while the subroutine runs (1), so the same identifier can be reused in other subroutines without a clash, and the memory is freed when the subroutine ends (1).
:::

::: example Write a function
Write a subroutine, in pseudo-code or program code, called `isEven` that takes an integer as a parameter and returns True if it is even and False otherwise. (3)

Python:
1. `def isEven(n):`
2. `    if n % 2 == 0:`
3. `        return True`
4. `    else:`
5. `        return False`

Subroutine heading with one parameter (1); remainder after dividing by 2 tested (MOD / %) (1); True and False returned correctly (1). `return n % 2 == 0` also earns full marks.
:::

::: example Trace nested calls
1. `SUBROUTINE double(x)`
2. `    RETURN x * 2`
3. `ENDSUBROUTINE`
4. `SUBROUTINE addOne(y)`
5. `    RETURN y + 1`
6. `ENDSUBROUTINE`
7. `OUTPUT addOne(double(5))`
8. `OUTPUT double(addOne(5))`

State the two outputs. (2)

Line 7: double(5) returns 10, then addOne(10) returns 11, so 11 (1).

Line 8: addOne(5) returns 6, then double(6) returns 12, so 12 (1).
:::

::: q
Explain one advantage of using subroutines when a team of programmers is developing a large program. (2)
---
Each programmer can write and test a different subroutine at the same time (1), so the program is finished sooner / each person can specialise (1). ::: watch
- A **function returns** a value; a **procedure does not**. If the question says "returns", use RETURN, not OUTPUT.
- **Use the return value** in the calling statement: assign it, output it or test it.
- Parameters are matched **by position**: the first value goes into the first parameter.
- Local variables exist **only while** the subroutine runs and are **only accessible inside** it: give both points when asked to describe them.
- Advantages need the **effect**, not just the feature: "reused" is weak; "written once and called many times, so changes are made in one place" scores.
- Don't read input inside a subroutine that the question says takes a parameter; the data should arrive through the parameter.
:::
