## What it is

Paper 1 is about **computational thinking**: taking a problem, breaking it down, stripping out what does not matter, and writing the steps a computer could follow. Three words carry most of the marks here, and they are easy to mix up.

**Algorithm.** An algorithm is a **sequence of steps that can be followed to complete a task**. A recipe, the instructions for flat-pack furniture and the method for long division are all algorithms. In computing, an algorithm might find the largest number in a list or check whether a password is long enough.

An algorithm is **not the same thing as a program**. A **program** is an **implementation** of an algorithm: the algorithm written in a particular programming language (Python, C#, VB.NET) so that a computer can run it. One algorithm can be implemented as many different programs, in different languages, by different programmers. The algorithm is the idea, and the program is one way of carrying it out. An algorithm written in English, pseudo-code or a flowchart cannot be run by a computer, but it is still an algorithm.

**Decomposition.** Decomposition means **breaking a problem into smaller sub-problems**, each of which does one identifiable job. Each sub-problem can itself be broken down further until every part is simple enough to solve directly. Building an online shop is too big to think about all at once. Decomposed, it becomes: show products, manage a basket, take payment and arrange delivery. "Take payment" decomposes again, into entering card details, checking them and confirming the order.

Why decompose?
- Each small part is **easier to understand, write and test** than the whole problem.
- Different people can **work on different parts at the same time**.
- Parts can be **reused**: a "check password" routine written once can be used wherever it is needed.
- In code, the sub-problems usually become **subroutines** (3.2.10).

**Abstraction.** Abstraction is **removing unnecessary detail** from a problem so you can focus on what matters for solving it. A London Underground map is the classic example. It keeps the order of stations and where lines connect, and throws away real distances, streets and bends. That is exactly the detail a passenger planning a route does not need. In computing:
- A football game models players as a position, a speed and a skill rating, not as every muscle and hair.
- A school's booking system stores a pupil's name, form and dietary needs, not their favourite film.
- A sat-nav treats the road network as junctions joined by roads with a length and a speed limit.

The test for abstraction is always: **what does this particular problem need?** A detail that is unnecessary for one problem can be essential for another.

| Term | What it means | Quick example |
|---|---|---|
| **Algorithm** | a sequence of steps that completes a task | the steps to find the highest score in a list |
| **Program** | an algorithm implemented in a programming language | that algorithm written in Python |
| **Decomposition** | breaking a problem into sub-problems | a quiz app split into: load questions, ask, mark, show score |
| **Abstraction** | removing unnecessary detail | a quiz question stored as text, options and answer, with no font or colour |

**A systematic approach.** Good programmers solve problems in an ordered way rather than typing code straight away:
1. **Understand the problem**: what are the inputs, what must be produced, and what are the rules?
2. **Decompose** it into sub-problems.
3. **Abstract**: decide which details matter and how to represent them as data.
4. **Design an algorithm** for each part, in **pseudo-code** or a **flowchart**.
5. **Implement** it as program code.
6. **Test** it and correct errors (3.2.11b).

**Pseudo-code** is a way of writing an algorithm that looks like code but is not tied to any language, so any programmer can read it and turn it into their own language. AQA prints every algorithm in its own **AQA pseudo-code**. In your answers you may use any sensible pseudo-code, but reading AQA's version quickly is essential.

| AQA pseudo-code | Meaning | Python equivalent |
|---|---|---|
| `total ← 0` | assignment: store 0 in total | `total = 0` |
| `CONSTANT VAT ← 0.2` | a constant, named in capitals | `VAT = 0.2` (by convention) |
| `name ← USERINPUT` | take input from the keyboard | `name = input()` |
| `OUTPUT 'Hi ', name` | display on screen | `print("Hi", name)` |
| `IF x > 5 THEN … ELSE … ENDIF` | selection | `if x > 5: … else: …` |
| `WHILE x < 10 … ENDWHILE` | loop, condition tested first | `while x < 10:` |
| `REPEAT … UNTIL x = 0` | loop, condition tested last | no direct equivalent |
| `FOR i ← 1 TO 5 … ENDFOR` | count-controlled loop, 1 to 5 inclusive | `for i in range(1, 6):` |
| `x ≠ y`, `x ≤ y`, `x ≥ y` | not equal, at most, at least | `x != y`, `x <= y`, `x >= y` |
| `# a comment` | a note for the reader, not run | `# a comment` |

Arrays in AQA pseudo-code are indexed from **0**, and `FOR` loop limits are **inclusive**: `FOR i ← 1 TO 5` runs with i = 1, 2, 3, 4 and 5.

- **Terminator** (rounded box): where the algorithm **starts** and **stops**.
- **Process** (rectangle): a calculation or assignment, such as `total ← total + mark`.
- **Input/output** (parallelogram): data coming in from the user, or going out to the screen.
- **Decision** (diamond): a question with exactly two exits, labelled **Yes** and **No** (or True and False). Selection and loops are both built from decisions.
- **Subroutine** (rectangle with double sides): a call to a separate, named block of steps.
- **Arrows** (flow lines) join the shapes and show which step comes next.

**Converting between them.** Each flowchart shape becomes one kind of statement. Parallelograms become `USERINPUT` or `OUTPUT`, rectangles become assignments, and a diamond becomes an `IF`. A diamond whose arrow **loops back up** to an earlier shape is a **loop**: a `WHILE` if the decision comes before the repeated steps, and a `REPEAT … UNTIL` if it comes after them. Going the other way, every `IF` or loop condition becomes a diamond, and every `ENDIF` is the point where the Yes and No paths join again.

::: terms
- **Algorithm**: a sequence of steps that can be followed to complete a task.
- **Program**: an implementation of an algorithm in a programming language, so that a computer can run it.
- **Decomposition**: breaking a problem into sub-problems, each doing one identifiable task, which may be broken down further.
- **Abstraction**: removing unnecessary detail from a problem so you can focus on what matters for solving it.
- **Pseudo-code**: a structured, language-independent way of writing an algorithm that looks like code but cannot be run.
- **Flowchart**: a diagram of an algorithm using standard shapes joined by arrows that show the order of the steps.
- **Terminator**: the rounded flowchart symbol that marks the start or the end of an algorithm.
- **Decision symbol**: the diamond flowchart symbol holding a yes/no question, with one exit for each answer.
- **Input/output symbol**: the parallelogram flowchart symbol for data entered by the user or displayed.
- **Process symbol**: the rectangular flowchart symbol for a calculation or assignment.
- **Assignment**: storing a value in a variable, written with an arrow in AQA pseudo-code, as in total ← 0.
:::

::: method
1. **Define questions:** give the textbook meaning in one sentence. Algorithm = sequence of steps to complete a task. Decomposition = breaking into sub-problems. Abstraction = removing unnecessary detail. Never swap the last two.
2. **"Describe how decomposition could be used" questions:** name **real sub-problems from the scenario** (for a quiz: load questions, ask a question, check the answer, keep score), not general benefits only.
3. **"Describe how abstraction could be used" questions:** say which details are **kept** and which are **ignored**, and why they are not needed for this problem.
4. **Algorithm versus program:** the program is the algorithm **implemented in a language**. An algorithm can exist in English, pseudo-code or a flowchart.
5. **Writing an algorithm:** use the form the question asks for. Work in order: inputs first, then processing, then outputs. Initialise totals and counters before any loop, and close every `IF`, `WHILE` and `FOR`.
6. **Flowchart questions:** use the right shape for each step, label both exits of every diamond Yes/No, and make sure every path reaches a Stop terminator.
:::

::: example Algorithm or program?
A student says: "My flowchart is not an algorithm because a computer cannot run it." Explain why the student is wrong. (2)

An algorithm is a sequence of steps to complete a task, and it can be written in any form, including a flowchart (1).

A program is an implementation of an algorithm in a programming language. The flowchart is an algorithm that has not yet been implemented as a program (1).
:::

::: example Flowchart to pseudo-code
A flowchart reads: Start → input `n` → process `total ← 0` → process `count ← 1` → decision "count ≤ n?". On Yes: process `total ← total + count`, then process `count ← count + 1`, then an arrow back up to the decision. On No: output `total` → Stop. Write the algorithm in pseudo-code. (4)

The parallelogram becomes an input, and the two rectangles before the decision are assignments (1):
1. `n ← USERINPUT`
2. `total ← 0`
3. `count ← 1`

The decision comes **before** the repeated steps and its Yes arrow loops back, so it is a WHILE loop (1):
- `WHILE count ≤ n`

The two rectangles inside the loop go inside it, in the same order (1):
- `    total ← total + count`
- `    count ← count + 1`
- `ENDWHILE`

The No exit leads to the output (1). The algorithm adds up the whole numbers from 1 to n:
- `OUTPUT total`
:::

::: example Writing an algorithm from a description
Write an algorithm in pseudo-code that asks the user for the prices of 3 items, adds them up and outputs the total. If the total is over £20, it should also output 'Free delivery'. (5)

Initialise the running total before the loop (1):
1. `total ← 0`

Use a count-controlled loop that runs exactly 3 times (1), taking an input each time (1):
- `FOR i ← 1 TO 3`
- `    price ← USERINPUT`
- `    total ← total + price`
- `ENDFOR`

Output the total after the loop has finished (1):
- `OUTPUT total`

Then check the condition with a selection statement (1):
- `IF total > 20 THEN`
- `    OUTPUT 'Free delivery'`
- `ENDIF`
:::

::: watch
- **Abstraction removes detail; decomposition breaks a problem down.** Swapping the two definitions is the most common lost mark in 3.1.
- In "describe how decomposition could be used" questions, **name sub-problems from the scenario**. General benefits alone usually score only one mark.
- For abstraction, say **what is ignored** and **what is kept**: the comparison earns the mark.
- An algorithm is **not** a program. A program is an algorithm **implemented in a programming language**.
- In flowcharts, inputs and outputs are **parallelograms**, not rectangles. Every diamond needs **two labelled exits**.
- Initialise totals and counters **before** a loop. Setting `total ← 0` inside the loop resets it every time round.
- Close every structure: `ENDIF`, `ENDWHILE`, `ENDFOR`, and `UNTIL` for a `REPEAT`.
:::
