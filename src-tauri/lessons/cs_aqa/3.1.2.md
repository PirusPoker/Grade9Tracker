## What it is

There is almost never only one way to solve a problem. Two programmers given the same task will often write two different algorithms, and **both can be correct**: they give the same output for every input. But one may take far longer to run than the other. This topic is about spotting **which algorithm is more efficient, and explaining why**.

**What efficiency means here.** For AQA GCSE, efficiency means **time efficiency**: how much work, and so how much time, an algorithm needs to finish. You will not be asked about memory efficiency in efficiency questions, and you do not need any formal notation such as Big-O. You compare algorithms in plain terms by **counting the steps**: how many times a loop runs, how many comparisons are made, or how many calculations are done.

A faster computer runs every algorithm faster, so efficiency is not about the hardware. It is about **how the amount of work grows** as the data gets bigger. An algorithm that does 10 extra comparisons on a list of 10 items might do 1,000,000 extra comparisons on a list of a million.

**Example 1: adding up the numbers 1 to n.** Algorithm A loops:
1. `total ← 0`
2. `FOR i ← 1 TO n`
3. `    total ← total + i`
4. `ENDFOR`
5. `OUTPUT total`

Algorithm B uses a formula:
1. `total ← n * (n + 1) DIV 2`
2. `OUTPUT total`

Both output 5050 when n is 100. But A does **100 additions**, one per loop pass, while B does **one calculation however big n is**. For n = 1,000,000, A loops a million times and B still does one calculation. B is more time-efficient.

**Example 2: a search that stops early.** Both algorithms below check whether a target value is in an array of 1,000 items.

Algorithm C always checks every item:
1. `found ← False`
2. `FOR i ← 0 TO LEN(items) - 1`
3. `    IF items[i] = target THEN`
4. `        found ← True`
5. `    ENDIF`
6. `ENDFOR`

Algorithm D stops as soon as it finds the target:
1. `found ← False`
2. `i ← 0`
3. `WHILE found = False AND i < LEN(items)`
4. `    IF items[i] = target THEN`
5. `        found ← True`
6. `    ENDIF`
7. `    i ← i + 1`
8. `ENDWHILE`

C **always** makes 1,000 comparisons. D makes only as many as it needs: if the target is the 3rd item, it makes 3 comparisons and stops. In the worst case (the target is last, or missing) D still makes 1,000, so it is never slower than C and usually much faster. The improvement comes from a **condition-controlled loop with an extra condition**, so the loop can end early.

**Example 3: checking pairs.** To check whether any name appears twice in a list of 10 names, algorithm E compares every name with every other name, both ways round:
1. `FOR i ← 0 TO 9`
2. `    FOR j ← 0 TO 9`
3. `        IF i ≠ j AND names[i] = names[j] THEN`
4. `            OUTPUT 'Duplicate found'`
5. `        ENDIF`
6. `    ENDFOR`
7. `ENDFOR`

Line 3 runs 10 × 10 = **100 times**. But comparing name 2 with name 5 and then name 5 with name 2 is the same check done twice. Algorithm F starts the inner loop just after i:
1. `FOR i ← 0 TO 8`
2. `    FOR j ← i + 1 TO 9`
3. `        IF names[i] = names[j] THEN`
4. `            OUTPUT 'Duplicate found'`
5. `        ENDIF`
6. `    ENDFOR`
7. `ENDFOR`

Now the comparison runs 9 + 8 + 7 + … + 1 = **45 times**, fewer than half as many, and the output is the same set of duplicates (each found once instead of twice).

**Common ways to make an algorithm more efficient:**

| Change | Why it saves time |
|---|---|
| **Stop the loop early** once the answer is known | no wasted passes after the target is found |
| **Avoid repeating work**, e.g. comparing each pair once | fewer comparisons |
| **Move a calculation out of a loop** if its value never changes | it is done once, not on every pass |
| **Use a formula** instead of a loop where one exists | one step instead of n steps |
| **Use a better algorithm** for the job, e.g. binary search on sorted data, merge sort on a big list | far fewer comparisons as the data grows |
| **Use ELSE IF** instead of a run of separate IFs | once one condition is true, the rest are skipped |

**Links to searching and sorting.** The searching and sorting algorithms in 3.1.3 and 3.1.4 are the standard examples of different algorithms for the same problem. Binary search on a sorted list of 1,000 items needs at most about 10 comparisons, while linear search may need 1,000. Merge sort is much faster than bubble sort on large lists. In both cases the faster algorithm comes with a cost or condition: binary search needs **sorted data**, and merge sort is **harder to write** and uses more memory.

**Efficient is not the only thing that matters.** On a list of 5 items, the difference between two algorithms is a few microseconds. A simple algorithm that is easy to read, write and test can be the better choice when the data is small. Efficiency matters most when the data is **large** or the algorithm runs **very often**.

**More code is not less efficient.** Algorithm D above has more lines than C but is more efficient. What counts is how many steps are **executed** when it runs, not how many lines are **written**.

::: terms
- **Efficiency**: how much time (number of steps) an algorithm needs to complete its task; at GCSE only time efficiency is examined.
- **Time efficiency**: a measure of how quickly an algorithm completes, judged by the number of operations it carries out.
- **Comparison**: a check of one value against another, such as items[i] = target; counting comparisons is a way to compare algorithms.
- **Loop pass**: one run through the body of a loop; fewer passes usually means a faster algorithm.
- **Worst case**: the input that makes an algorithm do the most work, such as the target being last in a linear search.
- **Best case**: the input that makes an algorithm do the least work, such as the target being first in a linear search.
- **Early exit**: ending a loop as soon as the answer is known, using a condition-controlled loop with an extra condition.
:::

::: method
1. **Check both algorithms do the same job.** If they give the same output, the question is about efficiency, not correctness.
2. **Count the work.** For each algorithm, count the loop passes, comparisons or calculations for the given data, or for a list of n items. Put numbers in your answer: "A makes 100 comparisons; B makes 45".
3. **Find where the saving comes from**: stopping early, not repeating comparisons, using a formula, or a calculation moved out of a loop.
4. **Write the explanation as a linked chain:** "B is more efficient because it stops looping when the item is found, so it makes fewer comparisons, so it takes less time."
5. **Mention data size.** The bigger the input, the bigger the difference in time.
6. **"Suggest a change to make it more efficient" questions:** name the change and say what work it removes, e.g. "replace the FOR loop with a WHILE loop that also stops when found is True, so no items are checked after the target is found".
7. **Never answer "it has fewer lines"**, "it uses less memory" or "it is easier to read" when the question asks about efficiency. Talk about **time** and **number of steps**.
:::

::: example Count the steps
Algorithm A sums the numbers from 1 to n with a FOR loop. Algorithm B uses `total ← n * (n + 1) DIV 2`. Explain why algorithm B is more efficient than algorithm A. (3)

A's loop runs n times, doing one addition per pass, so for n = 1,000 it does 1,000 additions (1).

B does a single calculation, whatever the value of n (1).

So B carries out far fewer operations and takes less time, and the gap grows as n gets larger (1).
:::

::: example Spot the wasted work
1. `count ← 0`
2. `FOR i ← 0 TO LEN(marks) - 1`
3. `    passMark ← 40`
4. `    IF marks[i] ≥ passMark THEN`
5. `        count ← count + 1`
6. `    ENDIF`
7. `ENDFOR`
Describe one change that would make this algorithm more efficient, and explain why. (2)

Move line 3, `passMark ← 40`, to before the loop (or make it a constant) (1).

Its value never changes, so assigning it on every pass is wasted work; done once, the loop does fewer operations (1).
:::

::: example Early exit
An algorithm uses a FOR loop to look through all 500 usernames in an array to check whether a new username is already taken. Explain how the algorithm could be made more efficient. (3)

Use a WHILE (condition-controlled) loop instead of a FOR loop (1).

Add a condition so the loop stops as soon as the username is found, e.g. `WHILE taken = False AND i < 500` (1).

Then, if the name is near the start, only a few comparisons are made instead of all 500, so the check takes less time (1).
:::

::: example Compare pair checks
Algorithm E checks for duplicates in a list of 10 names by comparing every name with every other name using two loops that each run from 0 to 9. Algorithm F's inner loop starts at i + 1. State how many comparisons each makes and explain which is more efficient. (4)

E: the inner comparison runs 10 × 10 = 100 times (1).

F: it runs 9 + 8 + … + 1 = 45 times (1).

F never compares a pair twice, and never compares a name with itself (1).

So F does fewer than half the comparisons for the same result, and is more time-efficient (1).
:::

::: q
State what is meant by the efficiency of an algorithm, as used in AQA GCSE questions. (1)
---
How much time (how many steps/operations) the algorithm needs to complete its task (1).
:::

::: q
A linear search of 200 items uses a FOR loop that always checks every item. The target is at position 4. How many comparisons does it make? How many would a version that stops when the target is found make? (2)
---
200 (1); 5, for positions 0 to 4 (1).
:::

::: q
Explain why the difference in efficiency between two algorithms matters more for large amounts of data. (2)
---
The number of steps grows with the amount of data, so the gap in steps between the algorithms grows too (1); on small data both finish almost instantly, but on large data the slower one could take a noticeably long time (1).
:::

::: q
Give two ways of making an algorithm more time-efficient. (2)
---
Any two (1 each): stop a loop early when the result is known; avoid repeated comparisons/calculations; move unchanging calculations out of a loop; use a formula instead of a loop; use a more efficient algorithm, e.g. binary search on sorted data; use ELSE IF so later conditions are skipped.
:::

::: q
A student says "Algorithm X is more efficient than Y because it has fewer lines of code." Explain why the student may be wrong. (2)
---
Efficiency depends on how many steps are executed when the algorithm runs, not how many lines are written (1); a short algorithm with a loop that always runs to the end can execute more steps than a longer one that stops early (1).
:::

::: q
Explain why using ELSE IF instead of three separate IF statements can make a grading algorithm more efficient. (2)
---
With ELSE IF, once one condition is true the remaining conditions are not checked (1); separate IFs test every condition every time, so ELSE IF makes fewer comparisons (1).
:::

::: watch
- Efficiency questions mean **time**. "Uses less memory", "fewer lines" or "easier to read" do not score.
- **Quantify** where you can: "the loop runs 100 times instead of 10" beats "it is quicker".
- Explain **why** it is faster (stops early, fewer comparisons), then **link** it to less time. A bare "it is faster" scores at most one mark.
- An early-exit search is **not faster in the worst case** (target last or missing). Say "usually" or "on average".
- Two algorithms can both be **correct**. Do not call the slower one "wrong".
- Do not use Big-O. It is not needed, and the marks are for plain explanations.
:::

::: test
Algorithm R:
1. `isVowel ← False`
2. `FOR v IN 'aeiou'`
3. `    IF ch = v THEN`
4. `        isVowel ← True`
5. `    ENDIF`
6. `ENDFOR`

Algorithm S:
1. `isVowel ← False`
2. `i ← 0`
3. `WHILE isVowel = False AND i < 5`
4. `    IF ch = SUBSTRING(i, i, 'aeiou') THEN`
5. `        isVowel ← True`
6. `    ENDIF`
7. `    i ← i + 1`
8. `ENDWHILE`

Both algorithms check whether the character ch is a vowel. Compare the efficiency of R and S when ch is 'a' and when ch is 'z'. (4)
---
- A. When ch is 'a', R still makes 5 comparisons (1).
- B. S makes only 1 comparison because the loop stops when isVowel becomes True (1).
- C. When ch is 'z' (not a vowel), both make 5 comparisons / S is no faster in this worst case (1).
- D. So S is at least as efficient as R and usually more efficient, because it can exit the loop early (1).

::: test
Algorithm E compares every pair of items in a list of 20 using two nested loops that both run from 0 to 19. Algorithm F's inner loop runs from i + 1 to 19. Explain why algorithm F is more efficient. (3)
---
E makes 20 × 20 = 400 comparisons (1); F compares each pair only once and never compares an item with itself, making 19 + 18 + … + 1 = 190 comparisons (1); fewer comparisons means less time for the same result (1).
:::

::: test
Explain why binary search is usually more efficient than linear search for a large sorted list. (3)
---
Binary search halves the number of items left to search after every comparison (1), whereas linear search checks items one at a time (1); so for a large list binary search needs far fewer comparisons, e.g. about 10 rather than up to 1,000 for 1,000 items (1).
:::

::: test
Explain why a less efficient algorithm might still be chosen by a programmer. (2)
---
It may be simpler to write, understand and test (1); and if the amount of data is small, the difference in time is too small to matter / a more efficient algorithm may need extra conditions, e.g. sorted data (1).
:::

::: test
A grading algorithm uses three separate IF statements:
1. `IF mark ≥ 70 THEN grade ← 'A' ENDIF`
2. `IF mark ≥ 50 AND mark < 70 THEN grade ← 'B' ENDIF`
3. `IF mark < 50 THEN grade ← 'C' ENDIF`

Explain how the algorithm could be made more efficient, and why the change works. (3)
---
Use one IF with ELSE IF/ELSE (1); e.g. IF mark ≥ 70 … ELSE IF mark ≥ 50 … ELSE … (1); once a condition is true the others are skipped, and the second condition no longer needs `mark < 70`, so fewer comparisons are made (1).
:::

::: test
A program must find whether a given number n (greater than 2) is prime. Write an algorithm, in pseudo-code or program code, that:
- takes n as input;
- tests whether any whole number from 2 up to n - 1 divides n exactly;
- stops testing as soon as a divisor is found, so that it is efficient;
- outputs 'Prime' or 'Not prime'. (6)
---
Example answer (pseudo-code):
1. `n ← USERINPUT`
2. `d ← 2`
3. `divisorFound ← False`
4. `WHILE d < n AND divisorFound = False`
5. `    IF n MOD d = 0 THEN`
6. `        divisorFound ← True`
7. `    ENDIF`
8. `    d ← d + 1`
9. `ENDWHILE`
10. `IF divisorFound THEN`
11. `    OUTPUT 'Not prime'`
12. `ELSE`
13. `    OUTPUT 'Prime'`
14. `ENDIF`
Mark points:
- A. n input and stored (1).
- B. Loop that tests divisors starting at 2 and going no further than n - 1 (1).
- C. Uses MOD (or equivalent) to test for an exact division (1).
- D. Loop stops early when a divisor is found, e.g. a second condition or break (1).
- E. Divisor variable increased inside the loop (1).
- F. Correct 'Prime'/'Not prime' output after the loop (1).
Accept Python (`while d < n and not divisor_found:`, `n % d == 0`), C# or VB.NET equivalents. Testing only up to n DIV 2 is also acceptable.
:::
