## What it is

An **algorithm** is a clear, ordered set of steps that solves a problem or does a task. You design the algorithm before you write real code, and OCR expects you to work with three ways of writing one — **pseudocode**, **flowcharts** and the **OCR Reference Language** — and to be able to **create, read, correct, complete and refine** them.

**Inputs, processes and outputs.** Every algorithm takes in data (**input**), does something with it (**process**), and gives a result (**output**). Working these out first tells you what the algorithm has to do.

**Flowcharts** show an algorithm as a diagram. Four shapes come up in J277:

| Shape | Name | Used for |
| --- | --- | --- |
| Rounded rectangle | Terminal | The Start and the Stop of the algorithm |
| Parallelogram | Input/Output | Reading an input, or printing an output |
| Rectangle | Process | An action or calculation, e.g. `total = total + 1` |
| Diamond | Decision | A yes/no question, e.g. `is count <= 5?`, with a branch for each answer |

Arrows, called **flow lines**, join the shapes and show the order they run in.

**Structure diagrams** show decomposition as a top-down tree: the whole problem sits at the top, is broken into sub-problems on the level below, and those are broken down again — the boxes lower down are the smaller, more detailed parts.

**Trace tables** let you check an algorithm by hand. You make a column for every variable, plus one for the output, and record each value as it changes, line by line, so you can see exactly what the algorithm does and spot where it goes wrong.

**Errors** come in two kinds. A **syntax error** breaks the rules of the language, so the code will not run at all — a misspelled keyword, a missing `endif`, an unclosed bracket. A **logic error** runs fine but gives the wrong result — the wrong formula, `<` where you needed `<=`, or a loop that repeats one time too few.

::: terms
- **Input**: data given to a program, e.g. typed by the user or read from a file.
- **Process**: what the program does with the data.
- **Output**: the result the program produces.
- **Structure diagram**: a diagram that shows how a problem is decomposed into smaller sub-problems, in levels.
- **Pseudocode**: a way of writing an algorithm in structured English-like statements that is not a real programming language.
- **Flowchart**: a diagram of an algorithm using standard symbols — terminator, process, decision, input/output — joined by arrows.
- **Trace table**: a table used to follow an algorithm step by step, recording the value of each variable after each line.
- **Syntax error**: an error that breaks the rules of the programming language, so the program will not translate or run.
- **Logic error**: an error that lets the program run but produces the wrong result.
:::

::: method
Completing a trace table for an algorithm:
1. Make one **column for each variable**, and one more column for **output** (anything printed).
2. Read the algorithm **line by line in the order it really runs** — follow loops back to the top, and take the correct branch at each decision.
3. Every time a variable's value **changes**, write the new value on a **new row** in that variable's column. Do not rub out the old value — the list of values is the answer.
4. Each time the algorithm **outputs** something, write it in the output column.
5. Stop when the algorithm ends — for a loop, that is when its condition becomes **false**.

Missing a column, or skipping a pass of the loop, loses the marks for the whole table — so go slowly and do every pass.
:::

::: example Inputs, processes and outputs
Identify the inputs, processes and outputs for a program that works out the average of two test marks. [3]

| Inputs | Processes | Outputs |
| --- | --- | --- |
| The first mark | Add the two marks together | The average mark |
| The second mark | Divide the total by 2 |  |

The two marks are the data going in, adding then dividing is what the program does with them, and the average is the result it gives back.
:::

::: example A filled trace table
Complete a trace table for this algorithm. [5]

1. `total = 0`
2. `count = 1`
3. `while count <= 5`
4. `  total = total + count`
5. `  count = count + 1`
6. `endwhile`
7. `print(total)`

Work through it line by line, adding a row each time a value changes:

| total | count | output |
| --- | --- | --- |
| 0 |  |  |
|  | 1 |  |
| 1 | 2 |  |
| 3 | 3 |  |
| 6 | 4 |  |
| 10 | 5 |  |
| 15 | 6 |  |
|  |  | 15 |

The loop runs while `count <= 5`. When `count` becomes 6 the condition is false, so the loop stops and `total`, which is 15, is printed.
:::

::: example Naming the flowchart shapes
A flowchart contains a diamond and a parallelogram. State what each one is used for. [2]

The **diamond** is a **decision** — a yes/no question with a separate branch for each answer, such as `is score > 10?`. The **parallelogram** is **input/output** — reading a value in, or printing a value out. (A rectangle would be a process, and a rounded rectangle a terminal, meaning Start or Stop.)
:::

::: example Syntax error or logic error?
A program should print the numbers 1 to 5, but the line `while count < 5` makes it stop at 4. Separately, the programmer typed `prnit(count)` by mistake. Classify each error and correct it. [3]

`while count < 5` is a **logic error** — the code runs, but it gives the wrong result because the test should be `count <= 5`. `prnit(count)` is a **syntax error** — `prnit` is not a valid keyword, so it breaks the rules of the language and the code will not run. The fixes: change `<` to `<=`, and correct the spelling to `print`.
:::

::: example Tracing a decision
Trace this algorithm and give the output when the input is 7. [3]

1. `input n`
2. `if n MOD 2 = 0 then`
3. `  print("even")`
4. `else`
5. `  print("odd")`
6. `endif`

| n | output |
| --- | --- |
| 7 |  |
|  | odd |

`7 MOD 2` is 1, not 0, so the condition is false and the `else` branch runs, printing `odd`.
:::

Draw a structure diagram for a program that runs a school tuck-shop till. [4]

Top level: Tuck-shop till (1).

Second level, the main sub-problems: Scan items; Calculate total; Take payment; Print receipt (1).

::: q
Name the four flowchart shapes and say what each is used for.
---
Terminal (rounded rectangle) for Start and Stop; input/output (parallelogram) for reading in or printing out; process (rectangle) for an action or calculation; decision (diamond) for a yes/no question that branches.
:::

::: q
Explain the difference between a syntax error and a logic error.
---
A syntax error breaks the rules of the language so the code will not run (e.g. a misspelled keyword). A logic error lets the code run but produces the wrong result (e.g. using `<` instead of `<=`).
:::

::: q
Give the input, process and output for a program that converts a price into a 10% deposit.
---
Input: the price. Process: work out 10% of the price (divide by 10). Output: the deposit amount.
:::

::: q
Why must a trace table have a new row every time a variable changes, rather than one final value?
---
Because the marks are for showing the algorithm working step by step. Recording every change proves you followed each pass in the right order; a single final value hides whether you traced it correctly.
:::

::: q
Trace `x = 3`, then `x = x + 4`, then `print(x)`. What is the output?
---
7. `x` starts at 3, then becomes 3 + 4 = 7, which is printed.
:::

::: q
What is a structure diagram used to show?
---
Decomposition: it breaks a problem down as a top-down tree, with the whole problem at the top and smaller, more detailed sub-problems on the levels below.
:::

::: q
A loop `for i = 1 to 3` should run three times but a student writes `for i = 1 to 2`. Is this a syntax or a logic error, and what happens?
---
A logic error — the code still runs, but the loop repeats only twice instead of three times, giving the wrong result.
:::

::: q
In a flowchart, which shape has more than one arrow coming out of it, and why?
---
The decision (diamond): it asks a yes/no question, so it needs one arrow out for "yes" and one for "no".
:::

::: watch
- **Every variable gets a column, every change gets a row.** Miss a column or skip a pass of the loop and the whole trace table's marks go.
- Trace **in the order the code actually runs** — loop back to the top of a `while`, and follow the branch a decision actually takes, not top to bottom.
- **Syntax error = will not run; logic error = runs but wrong.** Say which, and give the fix, when asked.
- Name flowchart shapes exactly: **terminal, process, decision, input/output** — "the box" or "the diamond thing" drops the mark.
- Keep **input, process and output** separate — a calculation is a process, not an input.
- A loop stops when its condition is **false**; write the row where the test fails so you know the loop has ended.
:::
