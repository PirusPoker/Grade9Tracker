## What it is

**Testing** is checking that a program does what it should — and finding the mistakes before a user does. A finished program that gives wrong answers is worse than useless, so testing is a planned part of writing software, not an afterthought.

**When you test.**
- **Iterative testing** happens *during* development: you test each part as you write it, fix any problems and re-test, building the program up in working pieces.
- **Final (terminal) testing** happens *at the end*, on the complete program: you check the whole thing against the original requirements, including how the parts work together.

**Types of error.**
- A **syntax error** breaks the rules of the language, so the program **will not run at all** — a missing `endif`, a misspelt keyword, an unclosed bracket. The translator reports it.
- A **logic error** breaks no language rules, so the program **runs but gives the wrong result** — using `+` where you meant `-`, or `<` where you meant `<=`. These are harder to find because nothing obvious fails; you only notice the output is wrong.

**Test data.** You choose inputs on purpose to test different situations:
- **Normal data** — sensible, everyday values the program should accept, such as an age of 25.
- **Boundary data** — values *exactly on the edge* of what is allowed, where mistakes cluster. For an age from 0 to 120, that is 0 and 120, and just outside, -1 and 121.
- **Invalid data** — the right type but outside the allowed range, which should be rejected, such as an age of 200.
- **Erroneous data** — the wrong type entirely, which should also be rejected, such as an age of "cat".

**Refining.** When a test's actual result does not match the expected result, you have found a fault. You correct the program and run the test again — and re-run earlier tests too, in case the fix has broken something else. This cycle of test, refine and re-test is how a program is made reliable.

::: terms
- **Testing**: running a program to check it works as intended and to find errors.
- **Iterative testing**: testing each part of a program repeatedly while it is being developed.
- **Final (terminal) testing**: testing the whole program at the end of development.
- **Syntax error**: an error that breaks the rules of the programming language, so the program will not run.
- **Logic error**: an error that lets the program run but produces an unexpected or wrong result.
- **Normal test data**: typical data that the program should accept.
- **Boundary test data**: data at the edges of the valid range, and just outside it.
- **Invalid test data**: data of the correct type that should be rejected because it is outside the valid range.
- **Erroneous test data**: data of the wrong type that should be rejected.
- **Refining**: improving an algorithm or program after testing to make it correct or more efficient.
:::

::: method
Test and refine a program:
1. **Test iteratively** as you build — check each part works before moving on.
2. **Test finally** at the end — run the whole program against its original requirements.
3. For each fault, decide the **type of error**: syntax (it will not run) or logic (it runs but is wrong).
4. Choose **test data** for every input: **normal**, **boundary**, **invalid** and **erroneous**, and write down the result you **expect**.
5. Run each test and compare the **actual result with the expected** one.
6. Where they differ, **refine** the program and **re-test**, including earlier tests, in case the change broke them.
:::

::: example Syntax error versus logic error
This should print whether someone can vote at 18 or over. Find the fault.

1. `age = int(input("Age: "))`
2. `if age >= 18 then`
3. `    print("Can vote")`
4. `else`
5. `    print("Cannot vote")`

There is no `endif`, so the selection is incomplete — a **syntax error**, and the program will not run. If instead the test read `age > 18`, the program would run but wrongly reject an 18-year-old — that would be a **logic error**.
:::

::: example Choosing test data
A program accepts a mark from 0 to 100. Give test data of each kind. [4]

- **Normal:** 57 — an ordinary value inside the range; should be accepted.
- **Boundary:** 0 and 100 — the exact edges; should be accepted. -1 and 101 test just outside and should be rejected.
- **Invalid:** 150 — a number, but outside the range; should be rejected.
- **Erroneous:** "cat" — not a number at all; should be rejected.

Boundary data is where off-by-one mistakes hide, so testing the edges matters most.
:::

::: example Finding a logic error by tracing
This should add the numbers 1 to 5, but it prints 10. Find the fault.

1. `total = 0`
2. `for i = 1 to 4`
3. `    total = total + i`
4. `next i`
5. `print(total)`

No language rule is broken, so it is a **logic error**. Tracing the loop shows `i` only reaches 4, so 5 is never added, and 1 + 2 + 3 + 4 is 10. Fixing line 2 to `for i = 1 to 5` makes it print 15.
:::

::: example Boundary testing a validation rule
A shop allows a quantity from 1 to 10. To test the range check, use boundary data on both edges.

| Test | Input | Expected |
| --- | --- | --- |
| Lowest allowed | 1 | Accepted |
| Highest allowed | 10 | Accepted |
| Just below | 0 | Rejected |
| Just above | 11 | Rejected |

If a quantity of 0 is wrongly accepted, the check was probably written `quantity < 0` instead of `quantity < 1` — a classic boundary logic error.
:::

::: example Iterative testing versus final testing
A student writes a quiz program in three parts: ask the questions, keep the score, show a grade.

With **iterative testing**, after writing the scoring they test it on its own with a few known answers to check the running total, then move on — each part checked as it is built.

With **final (terminal) testing**, once all three parts are joined they run the whole quiz from start to finish with a full set of test data, checking it meets the original requirements and that the parts work together.

Iterative testing catches faults early in one part; final testing proves the finished program works as a whole.
:::

::: q
What is the difference between a syntax error and a logic error?
---
A syntax error breaks the language rules so the program will not run; a logic error runs but produces the wrong result.
:::

::: q
What is boundary test data?
---
Values exactly on the edge of what is allowed, and just outside it, where mistakes are most likely.
:::

::: q
What is the difference between iterative testing and final testing?
---
Iterative testing checks each part during development; final (terminal) testing checks the whole finished program against its requirements.
:::

::: q
Give an example of erroneous data for an input that expects an age.
---
Text such as "cat" — the wrong type entirely, which should be rejected.
:::

::: q
Why is a logic error often harder to find than a syntax error?
---
The program still runs and produces output, so nothing obviously fails; you only spot it by noticing the result is wrong.
:::

::: q
For a mark from 0 to 100, give one piece of invalid data and one piece of boundary data.
---
Invalid: 150, a number out of range. Boundary: 0 or 100, the exact edges of the range.
:::

::: q
What should you do after fixing a fault found by a test?
---
Re-run the test to confirm the fix, and re-run earlier tests too in case the change has broken something that worked.
:::

::: q
Why is normal test data used?
---
To check the program works correctly with ordinary, sensible values that it is expected to accept.
:::

::: q
A program uses `<` where it should use `<=`. What type of error is this?
---
A logic error — the program runs but gives the wrong result at the boundary.
:::

::: watch
- **A syntax error stops the program running; a logic error runs and gives the wrong answer.** Say which one it is and why.
- **Boundary data sits exactly on the edge** of what is allowed — test the edge and just past it, where off-by-one bugs live.
- Know all four kinds of test data: **normal, boundary, invalid, erroneous**, and what each is for.
- **Invalid** data is the right type but out of range; **erroneous** data is the wrong type entirely — do not muddle them.
- **Iterative** testing runs during development; **final (terminal)** testing runs on the finished program.
- After a fix, **re-test** — including earlier tests — because one change can break something that already worked.
:::

::: test

---
Tests can only cover the cases the tester thought of; an untested input or path may still fail.
