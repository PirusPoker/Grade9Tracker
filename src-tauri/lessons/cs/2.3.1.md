## What it is

**Defensive design** means writing a program that keeps working even when things go wrong — when a user makes a mistake, types something unexpected, or deliberately tries to break it. You cannot assume input will be sensible, so you plan for misuse in advance.

Three ideas make up the topic.

**Anticipating misuse.** Think ahead about every way an input could be wrong: a letter where a number is expected, a blank box, a date like 32/13/2026, a negative age, an empty password. Good design handles each case gracefully instead of crashing.

**Input validation.** This is code that checks an input is sensible *before* the program uses it. It does **not** check the answer is *correct* — only that it is *reasonable*. The common checks are:
- **Presence check** — something was actually entered (not left blank).
- **Type check** — the input is the right type (a number, not text).
- **Range check** — a number lies between sensible limits, such as an age from 0 to 120.
- **Length check** — a string has an allowed number of characters, such as a password of at least 8.
- **Format check** — the input matches a required pattern, such as an email containing an "@".

If a check fails, the program gives a clear message and asks again, usually by looping until the input is valid.

**Authentication.** This confirms *who the user is* before letting them in — most often a username with a password or PIN. Note the difference from validation: validation asks "is this input sensible?"; authentication asks "are you allowed to do this?".

**Maintainability.** Programs are read and changed long after they are written, so make them easy to work with:
- **Meaningful identifier names** — `numberOfLives`, not `n`.
- **Comments** — short notes explaining *why* tricky code does what it does.
- **Indentation** — showing the structure of loops and selection.
- **Sub programs** — breaking the code into named functions and procedures rather than one long block.

::: method
Design a program defensively:
1. **Anticipate misuse** — for each input, list everything a user could type wrong or leave blank.
2. **Validate every input** with the right check: presence, type, range, length or format.
3. On a bad input, show a **clear error message** and **ask again**, looping until the value is valid.
4. Where access matters, **authenticate** the user with a username and a password or PIN.
5. Make it **maintainable**: meaningful names, helpful comments, consistent indentation, and sub programs for repeated or self-contained jobs.
:::

::: example A range check that re-asks
An age must be between 0 and 120. Keep asking until it is valid.

1. `age = int(input("Enter your age: "))`
2. `while age < 0 OR age > 120`
3. `    print("Age must be between 0 and 120.")`
4. `    age = int(input("Enter your age: "))`
5. `endwhile`

The `while` loop tests the value and repeats until the age is in range, so the program can never continue with a silly value. This is a **range check**.
:::

::: example A presence check
A name must not be left blank.

1. `name = input("Enter your name: ")`
2. `while name == ""`
3. `    print("You must enter a name.")`
4. `    name = input("Enter your name: ")`
5. `endwhile`

Comparing with the empty string "" checks that *something* was typed. This is a **presence check** — it does not prove the name is real, only that it is present.
:::

::: example Length check, then authentication
Check a password is long enough, then confirm the user's identity.

1. `const USER = "admin"`
2. `const PASS = "castle123"`
3. `name = input("Username: ")`
4. `password = input("Password: ")`
5. `while password.length < 8`
6. `    print("Password must be at least 8 characters.")`
7. `    password = input("Password: ")`
8. `endwhile`
9. `if name == USER AND password == PASS then`
10. `    print("Welcome, " + name)`
11. `else`
12. `    print("Login failed")`
13. `endif`

The loop is a **length check** — validation of the input's form. The `if` is **authentication** — confirming identity against stored details, with `AND` so both the username and password must match.
:::

::: example A format check for an "@"
An email address must contain an "@". Scan its characters to check.

1. `email = input("Enter your email: ")`
2. `found = false`
3. `for i = 0 to email.length - 1`
4. `    if email.substring(i, 1) == "@" then`
5. `        found = true`
6. `    endif`
7. `next i`
8. `if found == true then`
9. `    print("Looks valid")`
10. `else`
11. `    print("An email must contain @")`
12. `endif`

`substring(i, 1)` takes the single character at position `i`, and the loop sets `found` to true if any of them is "@". Checking the input fits a required pattern is a **format check**.
:::

::: example Making code maintainable
The same job, written carelessly then well. First, hard to follow:

1. `a = int(input("? "))`
2. `b = int(input("? "))`
3. `print(a * b / 2)`

Now the same result with meaningful names, a comment and a sub program:

1. `// Area of a triangle: half the base times the height`
2. `function triangleArea(base, height)`
3. `    return base * height / 2`
4. `endfunction`
5. `base = int(input("Enter the base: "))`
6. `height = int(input("Enter the height: "))`
7. `print(triangleArea(base, height))`

The output is identical, but the second version is far easier to read, reuse and fix — and maintainability marks are awarded exactly for naming, comments, indentation and sub programs.
:::

::: q
What is the difference between input validation and authentication?
---
Validation checks that an input is sensible; authentication checks who the user is and whether they are allowed access. They answer different questions.
:::

::: q
Name three types of validation check.
---
Any three of: presence, type, range, length and format checks.
:::

::: q
What does a range check do?
---
It confirms a number falls between an allowed lowest and highest value, for example an age from 0 to 120.
:::

::: q
Why does validation usually use a loop?
---
So that after a bad input the program can show an error and ask again, repeating until the value entered is valid.
:::

::: q
Does validation guarantee the input is correct? Explain.
---
No — it only checks the input is reasonable, not that it is the true or intended value; someone could enter a valid but wrong age.
:::

::: q
Give two things that make a program more maintainable.
---
Any two of: meaningful identifier names, comments, indentation and sub programs.
:::

::: q
Which check makes sure a box was not left empty?
---
A presence check, which tests that the input is not the empty string.
:::

::: q
Which check would ensure a password is at least 8 characters long?
---
A length check, which tests `password.length` against the minimum.
:::

::: q
Why is anticipating misuse part of defensive design?
---
Because users make mistakes or deliberately try to break a program, so planning for wrong input stops it crashing or behaving unpredictably.
:::

::: watch
- **Validation checks the input is sensible; authentication checks who the user is.** They are different questions and are easily confused — name the right one.
- Validation checks input is *reasonable*, **not correct** — a valid age can still be the wrong age.
- Learn the five checks by name: **presence, type, range, length, format**, and what each is for.
- After a failed check, **loop and ask again** — never let the program carry on with bad data.
- Maintainability marks come from **names, comments, indentation and sub programs** — give all four if asked.
- A **length check** uses `.length`; a **range check** uses `<` and `>` limits — match the check to the tool.
:::
